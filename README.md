# C++ Limit Order Book & Matching Engine

A C++17 limit order book and matching engine built to explore the data structures, matching rules, and performance trade-offs involved in electronic trading systems.

The engine processes incoming **limit orders**, applies **price-time priority**, supports partial and multi-level fills, and records completed trades. The current executable also includes a synthetic throughput benchmark.

## Features

- Separate bid and ask books, ordered by best available price
- Price-time priority: best price first, FIFO within a price level
- Full and partial fills, including a single incoming order matching multiple resting orders
- Cancellation and lookup of resting orders by ID
- Trade history and per-submission execution reports
- Optional trade notifications through a `TradeListener` interface
- Configurable preallocation of trade-history storage with `reserveTrades()`

**Scope:** This is an in-memory limit-order matching prototype, not a production exchange. It does not currently implement market orders, persistence, networking, concurrency, or exchange-grade order validation.

## Architecture

| Component | Responsibility |
| --- | --- |
| `Side.h` | Strongly typed `BUY` / `SELL` enum |
| `Order.h` | Order ID, integer price, quantity, and side |
| `Trade.h` | Buyer ID, seller ID, execution price, and executed quantity |
| `BookSide.h` | Price levels, FIFO queues, resting-order index, cancellation, and lookup |
| `MatchingEngine.h` | Bid/ask matching, partial fills, trade reports, and listener notifications |
| `TradeListener.h` | Abstract trade callback and console implementation |
| `main.cpp` | Command-line entry point for throughput benchmarking and assertion-based unit tests |

The two sides use the same `BookSide<Compare>` template:

```cpp
BookSide<std::greater<long long>> bids; // highest bid first
BookSide<std::less<long long>> asks;     // lowest ask first
```

Each side stores orders using:

```cpp
std::map<long long, std::list<Order>, Compare> orders;
std::unordered_map<int, std::list<Order>::iterator> orderIndex;
```

The map orders price levels, the list preserves insertion order at each price, and the hash map provides direct access to resting orders by ID.

### Matching rules

An incoming **BUY** matches the lowest-priced resting **SELL** while `buy.price >= bestAsk.price`. An incoming **SELL** matches the highest-priced resting **BUY** while `sell.price <= bestBid.price`.

Each execution quantity is `min(incoming.quantity, resting.quantity)`. The engine updates remaining quantities, removes fully filled resting orders, and inserts any unfilled incoming remainder into its own side of the book. Executions use the **resting order's price**.

`addOrder()` returns the trades generated by that submission and also appends them to the engine's cumulative trade history. A registered `TradeListener` receives an `onTrade()` callback for each execution.

## Design decisions and trade-offs

| Choice | Benefit | Trade-off |
| --- | --- | --- |
| `std::map` for price levels | Keeps prices sorted and exposes the best level at `begin()` | Tree navigation, pointer chasing, and logarithmic level operations |
| `std::list` per price level | FIFO order and constant-time erase with a valid iterator | Per-node allocation and weaker cache locality |
| `std::unordered_map` for order IDs | Average constant-time lookup of a resting order | Hash-table memory overhead and non-constant worst case |
| `std::vector<Trade>` for trade history | Contiguous storage and efficient append | Reallocation when capacity grows; unbounded history growth |
| Virtual `TradeListener` callback | Separates execution events from matching logic | Virtual dispatch and callback cost when a listener is registered |

`reserveTrades(n)` allows capacity to be allocated before processing a known workload. This avoids trade-history vector growth during the measured loop when the reservation is sufficient; it does **not** remove the work of creating execution reports.

## Complexity

Let **P** be the number of active price levels and **F** the number of executions generated by an incoming order.

| Operation | Complexity / notes |
| --- | --- |
| Access best resting order | O(1), assuming the side is nonempty |
| Add a resting order | O(log P) to locate/create a level, plus average O(1) hash-index insertion |
| Find a resting order by ID, within one side | Average O(1) hash lookup |
| Cancel a resting order, within one side | Average O(1) hash lookup and list erase, plus O(log P) price-level lookup/removal |
| Match an incoming order | Depends on F; each fill performs constant-time quantity updates and trade appends amortized, while deleting emptied price levels can cost O(log P) |

Engine-level cancellation and lookup check the bid side and then the ask side. Hash-table worst-case behavior, allocation costs, and listener callbacks are not captured by the simplified average-case bounds.

## Benchmark

**Setup:** 1,000,000 incoming orders per run, C++17, GCC Release build with `-O3 -DNDEBUG`, timed using `std::chrono::steady_clock`. Order generation and result printing are outside the timed section. Each configuration below reports the **median of five runs**.

| Workload | Median throughput | Median elapsed time |
| --- | ---: | ---: |
| Random buy/sell orders, prices 95–105, quantities 1–100 | 6.48 million orders/s | 0.154233 s |
| No matching: 1M BUY orders at price 100 | 10.06 million orders/s | 0.0994355 s |
| Frequent matching: alternating BUY/SELL at price 100, quantity 10 | 12.14 million orders/s | 0.0823444 s |
| Frequent matching + `reserveTrades(500000)` | 13.18 million orders/s | 0.0758854 s |

The frequent-matching workload produced **500,000 trade records** for 1,000,000 incoming orders. Reserving trade-history capacity was associated with an approximately **8.5% increase in median throughput** relative to the unreserved frequent-matching configuration.

These measurements are **workload-dependent batch throughput**, not per-order latency or end-to-end trading-system performance. Different workloads also change the number of live orders, memory allocations, and matching operations, so the results do not isolate a single bottleneck. The reserve comparison was not an interleaved controlled experiment; additional profiling and repeated A/B runs would be needed to attribute the observed improvement confidently.

By default, `main.cpp` runs the **frequent-matching benchmark with trade-history preallocation**. Passing `test` runs the four assertion-based tests instead. The other benchmark scenarios were measured by changing the order-generation code; they are not currently selectable via command-line arguments.

## Tests and validation

Four assertion-based tests were executed successfully in a Debug build (**4/4 passed**):

- **Double Cancel:** Cancelling an order twice returns the expected results, and the order is no longer found.
- **Cancel Middle Order:** Cancelling an order in the middle of a price level preserves FIFO execution order for the remaining orders.
- **Partial Fill Remaining:** A partial execution leaves the correct remaining quantity and order book state.
- **Multiple Fills:** One incoming order matches three resting price levels in the correct price order, with accurate trade quantities and remaining orders.

The alternating-order benchmark also produced the expected **500,000 trade records** for 1,000,000 incoming orders. This is a benchmark sanity check, not a substitute for automated assertions.

Run tests with the `test` command-line argument. **Use a Debug build:** `assert()` is disabled by `-DNDEBUG` in Release builds. The project does not yet have a dedicated test target or CI workflow.

Potential follow-up tests include duplicate IDs, invalid quantities/prices, and price-time priority across more edge cases. The current `BookSide` rejects duplicate IDs only within that side; the engine does not enforce a globally unique order ID across both sides.

## Build and run

Requirements: a C++17-capable compiler, CMake, and Ninja. The commands below use the executable name `OrderBook.exe` from the development setup.

**Release benchmark (Windows PowerShell)**

```powershell
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
.\build\OrderBook.exe
```

**Debug tests (Windows PowerShell)**

```powershell
cmake -S . -B build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build-debug
.\build-debug\OrderBook.exe test
```

Expected test output:

```text
Double Cancel Test Passed!
Cancel Middle Order Test Passed!
Partial Fill Remaining Test Passed!
Multiple Fills Test Passed!
All tests passed!
```
